3. PATIENT MOBILE APP / WEB: AUTHENTICATION
================================================================

   A. LOGIN PAGE
   ─────────────────────────────────────────────────────────────
   URL: /patient/login
   Role: Public (unauthenticated)
   Device: Mobile app & Web

   Komponen:
     - Header: Logo + "Masuk ke Akun"
     - Form:
        * Email field (email input, placeholder: "email@example.com")
        * Password field (password input, placeholder: "••••••••")
        * Checkbox "Ingat saya" (opsional)
        * Button "Masuk" (primary, full width, disabled jika form invalid)
     - "Lupa Password?" link (secondary)
     - CTA: "Belum punya akun? [Daftar Sekarang]" (tertiary link)

   LOGIC FLOW:
     1. User input email & password.
     2. Validasi frontend:
        - Email not empty & valid format.
        - Password not empty & >= 8 karakter.
     3. Submit POST /auth/login dengan body { email, password }.
     4. Backend:
        - Cek email exist, validate password (bcrypt).
        - Jika gagal 5× dalam 5 menit → rate limit 429 lock 5 menit.
        - Jika berhasil: generate JWT token (expiry 7 hari), return { token, role, patient_id, name }.
     5. Frontend:
        - Simpan token di secure storage (localStorage atau secure storage for mobile).
        - Navigasi ke /patient/home (atau /patient/bookings).
     6. Error handling:
        - Gagal: tampilkan "Email atau password salah" atau "Akun terkunci sementara".

   B. REGISTER PAGE
   ─────────────────────────────────────────────────────────────
   URL: /patient/register
   Role: Public
   Device: Mobile app & Web

   Komponen:
     - Header: Logo + "Buat Akun Baru"
     - Form:
        * Nama Lengkap (text input, wajib)
        * Email (email input, wajib, harus unik)
        * Nomor HP (tel input, wajib, format Indonesia, minimal 10 digit, max 13)
        * Password (password input, wajib, >= 8 karakter, harus include uppercase, lowercase, number, symbol)
        * Konfirmasi Password (password input, wajib, harus sama dengan password)
        * Checkbox "Saya setuju dengan ToS & Privacy Policy" (wajib)
        * Button "Daftar" (primary, full width, disabled jika form invalid)
     - CTA: "Sudah punya akun? [Masuk]" (tertiary link)
     - Password requirements indicator (visual: requirements list, check/cross marks)

   LOGIC FLOW:
     1. User input semua field.
     2. Validasi frontend (real-time):
        - Nama: not empty, min 3 karakter.
        - Email: valid format, unique check (optional di frontend, definite di backend).
        - HP: Indonesian format, 10-13 digits, starts with 0 or +62.
        - Password: >= 8 karakter, uppercase, lowercase, number, symbol.
        - Konfirmasi password: sama dengan password.
        - Checkbox: checked.
     3. Submit POST /auth/register dengan body { full_name, email, phone, password }.
     4. Backend:
        - Validasi ulang semua field.
        - Cek email & phone unique (jika tidak, return 409).
        - Hash password (bcrypt), simpan user ke database dengan role PATIENT.
        - Kirim email verification link (opsional untuk V1, atau skip).
     5. Frontend:
        - Jika berhasil, redirect ke login page dengan pesan "Akun berhasil dibuat. Silakan login."
     6. Error handling:
        - Email already exists → "Email sudah terdaftar"
        - Phone already exists → "Nomor HP sudah terdaftar"
        - Server error → "Terjadi kesalahan. Coba lagi nanti."

   C. FORGOT PASSWORD PAGE
   ─────────────────────────────────────────────────────────────
   URL: /patient/forgot-password
   Role: Public
   Device: Mobile app & Web

   Komponen:
     - Header: "Reset Password"
     - Step 1 (Email verification):
        * Text: "Masukkan email Anda untuk reset password"
        * Email field
        * Button "Kirim Link Reset" (primary)
     - Step 2 (after submit, if email exists):
        * Success message: "Link reset password telah dikirim ke email Anda"
        * Text: "Buka email dan klik link untuk melanjutkan"
        * Link: "Kembali ke Login"

   LOGIC FLOW:
     1. User input email.
     2. Validasi frontend: email not empty & valid format.
     3. Submit POST /auth/forgot-password dengan body { email }.
     4. Backend:
        - Cek email exist di database.
        - Generate reset token (random, expiry 1 jam).
        - Simpan reset token ke database (tokens table atau users table).
        - Kirim email dengan link: 
          https://[domain]/patient/reset-password?token=[reset_token]
        - Return 200 OK (always, don't reveal if email exists untuk security).
     5. Frontend:
        - Tampilkan success message.
        - (Opsional) Countdown timer: "Tidak terima email? Coba lagi dalam 60 detik."
     6. User klik link email → navigasi ke reset password page dengan token query param.

   D. RESET PASSWORD PAGE
   ─────────────────────────────────────────────────────────────
   URL: /patient/reset-password?token=[reset_token]
   Role: Public (unauthenticated, tapi dengan valid reset token)
   Device: Mobile app & Web

   Komponen:
     - Header: "Buat Password Baru"
     - Form:
        * Password Baru (password input, wajib, >= 8, uppercase, lowercase, number, symbol)
        * Konfirmasi Password Baru (password input, wajib, sama dengan password baru)
        * Button "Reset Password" (primary)
     - Password requirements indicator

   LOGIC FLOW:
     1. Parse reset_token dari URL query.
     2. Frontend validasi token format (optional, definite di backend).
     3. Validasi form: passwords >= 8, requirements met, match.
     4. Submit POST /auth/reset-password dengan body { token, new_password }.
     5. Backend:
        - Validasi token exist & not expired.
        - Cek user associated dengan token.
        - Hash password baru, update user.password.
        - Delete/invalidate reset token.
        - Return 200 OK.
     6. Frontend:
        - Tampilkan success message: "Password berhasil direset. Silakan login dengan password baru."
        - Redirect ke /patient/login setelah 2-3 detik.
     7. Error handling:
        - Token invalid/expired → "Link reset tidak valid atau sudah kadaluarsa. [Minta link baru]"
        - Password tidak sesuai syarat → "Password harus minimal 8 karakter, include huruf besar, kecil, angka, simbol"

     2. Klik "Bayar Sekarang":

          {
            "branch_id", "doctor_id", "appointment_date", "session_id",
            "patient_id", "dp_amount": 50000
          }

          * Validasi semua field.
          * Cek slot masih tersedia (booking concurrency check).
          * Create booking record dengan status PENDING_PAYMENT.
          * Generate 6-digit alphanumerik booking code (FR-15).
          * Simpan booking ke database.
          * Return { "booking_id", "transaction_url" }.
        - Frontend:
          * Show loading spinner: "Sedang memproses..."
          * Redirect ke payment page (Midtrans payment redirect).
     3. Klik "Edit Booking" → navigate back ke Step 1 (preservasi data atau reset?).
     4. Klik "Batal Booking" → confirm dialog "Apakah yakin ingin batal?" → navigate back to /patient/home.

   C. PAYMENT PAGE (REDIRECT TO MIDTRANS)
   ───────────────────────────────────────────────────────
   URL: Midtrans hosted payment page (external)
   Role: PATIENT
   Device: Mobile app & Web

   Komponen (handled by Midtrans):
     - Midtrans payment UI (payment method selection, details entry, etc.)

   LOGIC FLOW:
     1. Frontend receive transaction_url from /bookings POST response.
     2. Redirect to transaction_url (window.location = url).
     3. User select payment method, enter details, submit.
     4. Midtrans process payment.
     5. On success:
        - Midtrans send webhook POST /webhook/payment-confirmation ke backend.
        - Backend validate webhook signature, update booking status → PAYMENT_CONFIRMED.
        - Midtrans redirect user ke success page (URL configured in Midtrans dashboard).
        - Frontend navigate to /patient/bookings/:booking_id (detail halaman dengan status PAYMENT_CONFIRMED).
     6. On failure:
        - Midtrans redirect ke failure page.
        - User dapat retry atau batal.

   B. QUEUE TABLE / LIST (REAL-TIME, POLLING 3 DETIK)
   ─────────────────────────────────────────────────────────────
   Komponen:
     - Table columns:
        * Nomor (Queue Number)
        * Nama Pasien
        * Dokter
        * Status (badge: color-coded)
        * Waktu Check-in
        * Aksi (buttons)
     - Rows (sorted by queue number ascending):

          - Queue number (prominent, large font)
          - Nama pasien (or pasien code jika privacy concern)
          - Dokter assignment
          - Status badge (WAITING = blue, CALLED = orange, IN_SERVICE = purple, COMPLETED = green, NO_SHOW = red)
          - Check-in time
          - Action buttons:
            * Jika WAITING: [Panggil] [Selesai] [No-show] [Hapus]
            * Jika CALLED: [Panggil Ulang] [Mulai Layani] [No-show]
            * Jika IN_SERVICE: [Selesai] [No-show]
            * Jika COMPLETED/NO_SHOW: [Hapus]

   LOGIC FLOW (Real-time Queue):
     1. Load: GET /queues/branch/:branch_id?date=[date] (polling every 3 seconds).
     2. Backend return list of queue records untuk cabang & tanggal tersebut.
     3. Frontend display table, refresh setiap 3 detik dengan update UI (preservasi scroll position).
     4. Actions:
        a) **Panggil (Call)**:
           - Admin klik tombol "Panggil" pada baris WAITING.
           - Confirm dialog: "Panggil pasien [Nama]?"
           - POST /queues/:queue_id/call.
           - Backend: update status → CALLED, publish event 'patient.called', kirim FCM ke pasien.
           - Frontend: update row status immediately, show toast "Pasien dipanggil".
        b) **Mulai Layani (Start Service)** (dari CALLED):
           - Admin klik tombol (atau "Mulai Layani").
           - POST /queues/:queue_id/start-service.
           - Backend: update status → IN_SERVICE.
           - Frontend: update row, show toast.
        c) **Selesai (Complete)** (dari WAITING atau IN_SERVICE):
           - Admin klik "Selesai".
           - Modal: select "Tindakan apa yang dilakukan pasien?" (dropdown atau autocomplete, misal "Scaling", "Filling", "Check-up", etc) — OPTIONAL jika admin tidak perlu input, biarkan dokter input di EMR.
           - POST /queues/:queue_id/complete { action (optional) }.
           - Backend: update status → COMPLETED, remove from display, publish event.
           - Frontend: remove row dari table atau grey out, show toast.
        d) **No-show**:
           - Admin klik tombol "No-show".
           - Confirm dialog: "Tandai pasien tidak datang? DP akan hangus."
           - POST /queues/:queue_id/no-show.
           - Backend: update status → NO_SHOW, update booking status → NO_SHOW, deduct DP, audit log.
           - Frontend: remove row atau grey out, show toast.
        e) **Hapus (Delete)** (dari COMPLETED atau NO_SHOW):
           - Admin klik "Hapus".
           - Confirm dialog: "Hapus dari antrian? Data akan tetap tersimpan di history."
           - DELETE /queues/:queue_id.
           - Backend: delete queue record (or soft delete, mark as inactive).
           - Frontend: remove row, show toast.

16. LOGIC FLOW UMUM (CROSS-CUTTING)
================================================================

   A. AUTHENTICATION & AUTHORIZATION
      ─────────────────────────────────────────────────────────
      - All endpoints (except /auth, /health, public pages) require JWT token.
      - Role-based access control:
        * PATIENT: /patient/*, /auth/patient-*
        * ADMIN_BRANCH: /admin/*, /auth/admin-*
        * DOCTOR: /doctor/*, /auth/doctor-*
      - Admin & Doctor: row-level security, can only access own branch data (branch_id filter).
      - Patient: can only access own bookings & encounters (patient_id filter).

   B. VALIDASI & ERROR HANDLING
      ─────────────────────────────────────────────────────────
      - Frontend validation: real-time feedback, disable submit jika invalid.
      - Backend validation: all inputs validated (Zod), return 400 dengan error detail.
      - Error messages: Bahasa Indonesia, deskriptif, actionable.
      - Examples:
        * 400 Bad Request: "Email format tidak valid"
        * 409 Conflict: "Email sudah terdaftar"
        * 401 Unauthorized: "Silakan login terlebih dahulu"
        * 403 Forbidden: "Anda tidak memiliki akses ke halaman ini"
        * 429 Too Many Requests: "Terlalu banyak percobaan. Coba lagi dalam [X] menit"
        * 500 Server Error: "Terjadi kesalahan server. Tim kami sedang menangani. Coba lagi nanti."
      - Rate limiting: 5 failed login attempts dalam 5 menit → lock akun 5 menit.

   C. REAL-TIME UPDATES (QUEUE, PAYMENTS)
      ─────────────────────────────────────────────────────────
      - Queue updates: polling every 3 seconds (fallback) atau WebSocket (preferred).
      - TV display updates: polling every 2-3 seconds (more frequent).
      - Payment webhook: real-time via Midtrans webhook (synchronous).
      - FCM notifications: push notification ke mobile app (async).
      - Event-driven: use RabbitMQ untuk publish events (booking_confirmed, patient.called, etc).

   D. NOTIFIKASI (FCM & EMAIL)
      ─────────────────────────────────────────────────────────
      - FCM push notifications:
        * Booking confirmed: "Booking Anda dikonfirmasi. Kode: [6-digit]. Datang sebelum [waktu]"
        * Patient called: "Dokter memanggil Anda. Nomor: [N]"
        * EMR completed: "Kunjungan selesai. Lihat EMR Anda" (link ke app)
      - Email notifications:
        * Registration confirmation (optional)
        * Booking confirmation: "Booking Anda berhasil. Kode: [6-digit]"
        * Payment confirmation: "Pembayaran diterima. Silakan check-in di klinik"
        * EMR completion: "Rekam medis kunjungan Anda telah selesai" (link untuk lihat)
      - Sendiri: use Resend (or similar email service).
      - Mock untuk testing (development environment).

   E. AUDIT LOG
      ─────────────────────────────────────────────────────────
      - Immutable, append-only, no UPDATE/DELETE.
      - Events logged:
        * Authentication: LOGIN, LOGOUT, FAILED_LOGIN, CHANGE_PASSWORD
        * Booking: BOOKING_CREATED, BOOKING_CANCELLED, BOOKING_CONFIRMED
        * Payment: PAYMENT_REDIRECT, PAYMENT_CONFIRMED, PAYMENT_INPUT
        * Queue: CHECKIN, QUEUE_CALL, SERVICE_START, SERVICE_COMPLETE, NO_SHOW
        * EMR: EMR_CREATED, EMR_UPDATED, EMR_COMPLETED
        * Inventory: INVENTORY_CREATE, INVENTORY_UPDATE, INVENTORY_DELETE
        * Schedule: SCHEDULE_OVERRIDE
        * Reconciliation: RECONCILIATION_COMPLETED
      - Each log entry: timestamp, event_type, user_id, user_name (Bahasa Indonesia), 
        affected_resource_id, description, metadata (JSON).
      - Stored in audit_logs table (immutable), indexed by branch_id & date for fast retrieval.

   F. IDEMPOTENCY (PAYMENT)
      ─────────────────────────────────────────────────────────
      - Each payment request: generate unique request_id (UUID), store di database dengan unique constraint.
      - Midtrans webhook: IF request_id already exist, return existing payment response (no duplicate charge).
      - Prevents duplicate charges jika webhook di-retry.

   G. DATA SECURITY & PRIVACY
      ─────────────────────────────────────────────────────────
      - JWT tokens: HttpOnly cookie (preferred) atau localStorage (fallback).
      - HTTPS only (enforced).
      - Passwords: bcrypt (cost 12+), no plaintext.
      - Sensitive data (DP amount, payment method): encrypted di database (optional, per compliance requirement).
      - Patient privacy: EMR diagnosa dapat disembunyikan dari admin (policy decision).
      - TV display: hanya nomor antrian (no patient names, untuk privacy).

   H. DATABASE BACKUPS
      ─────────────────────────────────────────────────────────
      - Automated daily backup: 02:00 (local time).
      - Backup destination: local storage + Supabase auto-backup.
      - Manual backup: admin dapat trigger via /admin/settings.
      - Restore procedure: tested & documented (untuk disaster recovery).
