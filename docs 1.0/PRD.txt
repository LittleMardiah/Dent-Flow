2. RINGKASAN EKSEKUTIF
   
   LATAR BELAKANG:
   Klinik gigi 3 cabang (A,B,C) dengan 8 dokter spesialis per cabang (total 24 dokter) 
   mengalami:
   - Antrean manual dan tidak terkelola real-time
   - Rekam medis (EMR) tidak terpusat antar cabang
   - Pembayaran & booking masih manual/cash-based
   - Audit trail tidak terdokumentasikan
   - Check-in process tidak kondusif (self-service chaos)
   - Admin involvement di payment bottleneck

   SOLUSI PRODUK:
   Sistem modular monolith (Modulith) berbasis Node.js/Express dengan:
   - Backend: Node.js + Express (event-driven dengan RabbitMQ opsional)
   - Database: PostgreSQL (1 instance, multi-tenant dengan branch_id)
   - Cache: Redis (queue management, atomic counters)
   - Storage: MinIO (file uploads)
   - Payment: Midtrans Sandbox (webhook untuk DP confirmation)
   - Frontend Web: Next.js (admin + dokter)
   - Mobile: Flutter Android (optional V1, live demo via APK)
   - Landing Page: Next.js (public, dengan AI chat support)
   - TV Display: Real-time queue display per cabang
   
   USER & ROLE:
   - Pasien: Booking online (mobile app/web), payment via Midtrans, check-in via admin, lihat history EMR
   - Admin Cabang: Manage queue, input kode booking check-in, view invoice, lihat EMR (read-only), backup, audit log, manage stok
   - Dokter: Input EMR, call pasien dari queue, input tindakan & resep, lihat invoice (read-only)

   ✅ EMR terpusat (dokter input 1x, pasien lihat filtered fields)
   ✅ Auto-Invoice saat EMR completed (eliminate admin invoice creation burden)
   ✅ Multi-tenant isolation (3 cabang, data completely separate)
   ✅ Audit log immutable (Bahasa Indonesia, 15+ event types)
   ✅ Smart appointment suggestion via AI chat (landing page)
   ✅ Simple payment tracking + export CSV (untuk manual reconciliation)

5. DETAILED FEATURE SPECIFICATIONS

5.1 PAYMENT GATEWAY FLOW (NEW - v10)
   
   ARCHITECTURE:
   - Provider: Midtrans (Sandbox environment)
   - Tunnel: Ngrok (local → public HTTPS)
   - Flow Type: Redirect flow (server-to-server webhook confirmation)
   - Payment Status: Pending → Settlement (DP Rp 50.000)
   
   USER FLOW:
   1. Pasien selesai booking, klik "Bayar Sekarang"
   2. System redirect ke Midtrans payment page
   3. Pasien select payment method (simulated, no real money)
   4. Pasien complete payment (instant, sandbox mode)
   5. Midtrans send webhook → /webhook/payment-confirmation
   6. Backend update booking status: PENDING_PAYMENT → PAYMENT_CONFIRMED
   7. System return to mobile/web: Booking confirmation page
   8. Display: Kode Booking + Nama Dokter + Spesialis + Cabang + Jadwal (Hari & Tanggal)
   9. Pasien see "Silakan datang ke Admin untuk Check-in"
   
   API ENDPOINTS:
   POST /api/bookings/{id}/payment-redirect
   - Request: booking_id, email, nominal (Rp 50.000)
   - Response: Redirect URL ke Midtrans payment
   - Headers: Authorization (JWT)
   
   POST /webhook/payment-confirmation
   - Request: (from Midtrans) transaction_id, status, booking_id
   - Logic: Verify signature → Update booking → FCM notification
   - Response: 200 OK (Midtrans requirement)
   
   DATABASE CHANGES:
   - bookings table: ADD COLUMN payment_gateway_id (varchar, Midtrans transaction ID)
   - bookings table: ADD COLUMN payment_status (PENDING_PAYMENT | PAYMENT_CONFIRMED | FAILED)
   - bookings table: ADD COLUMN payment_confirmed_at (timestamp)
   - audit_logs: ADD event type PAYMENT_CONFIRMED_BY_GATEWAY
   
   ERROR HANDLING:
   - Payment timeout: Booking stay PENDING_PAYMENT (can retry 24 jam)
   - Webhook failure: Retry logic 3x dengan exponential backoff
   - Signature mismatch: Log & alert, do not update booking
   - Network error: Fallback polling (client check status setiap 5 detik)
   
   TESTING:
   - Simulate successful payment via Midtrans simulator
   - Simulate payment failure (insufficient balance)
   - Test webhook signature verification
   - Test idempotency (duplicate webhook doesn't duplicate booking)

5.2 MANDATORY ADMIN CHECK-IN (NEW - v10)
   
   RATIONALE:
   - Prevent check-in chaos (self-service problematic di Indonesian market)
   - Operasional control: Admin verify pasien benar-benar datang
   - Fair queue assignment: Prevent fraud/code sharing
   - Clinical workflow: Admin greet pasien, coordinate dengan dokter
   
   PROCESS:
   1. Pasien tiba di klinik (sudah bayar DP via Midtrans)
   2. Pasien approach admin desk
   3. Admin ask: "Kode booking Anda berapa?"
   4. Admin input kode booking ke admin panel (6-digit field)
   5. System validate:
      - Kode valid (exist di database)?
      - Booking status = PAYMENT_CONFIRMED?
      - Waktu saat ini dalam sesi dokter (check jadwal)?
      - Kode belum pernah di-check-in sebelumnya?
   6. Validation success: Generate nomor antrean (Redis atomic counter)
   7. Update booking: status = CHECKED_IN, queue_number = X, checked_in_at = NOW
   8. Display nomor di admin screen (immediate)
   9. Push FCM: "Nomor antrian Anda: 05. Silakan menunggu di ruang tunggu"
   10. TV display: Update real-time (add nomor 05 ke QUEUE list)
   
   VALIDATION LOGIC:
   ```
   if (kode.valid && booking.status == PAYMENT_CONFIRMED 
       && NOW within booking.sesi_waktu 
       && !kode.checked_in_before) {
       generate_queue_number()
   } else {
       return error dengan detail reason
   }
   ```
   
   ERROR MESSAGES:
   - "Kode booking tidak ditemukan"
   - "Kode sudah digunakan sebelumnya"
   - "Sesi sudah berakhir"
   - "Pembayaran belum dikonfirmasi"
   - "Booking belum dibuat"
   
   PREVENT RE-CHECK-IN:
   - If kode already checked-in today, show: "Anda sudah check-in, nomor antrian: 05"
   - Do not generate duplicate queue number
   
   WALK-IN SUPPORT:
   - Admin can add walk-in pasien tanpa kode (skip validation)
   - Input: Nama pasien, pilih spesialis, auto-generate kode & queue number
   - Walk-in status: WALK_IN (untuk audit log tracking)
   - Queue priority: Mixed FIFO dengan online bookings (fair system)
   
   UI MOCKUP (ADMIN PANEL):
   ```
   ┌──────────────────────────────┐
   │ CHECK-IN PASIEN              │
   ├──────────────────────────────┤
   │ Masukkan Kode Booking:       │
   │ [_____________________]      │
   │                              │
   │ [CARI PASIEN] [ADD WALK-IN]  │
   │                              │
   ├──────────────────────────────┤
   │ HASIL:                       │
   │ Nama: Budi Santoso           │
   │ Spesialis: Sp.BM             │
   │ Dokter: Dr. Siti Nurhaliza   │
   │ Jadwal: 09:00-12:00          │
   │ ✅ Nomor Antrian: 05         │
   │                              │
   │ [SIMPAN] [CANCEL]            │

   ```

5.3 TV QUEUE DISPLAY (NEW - v10)

   OVERVIEW:
   Real-time antrian display untuk pasien di ruang tunggu. Menampilkan semua 8 spesialis
   dengan nomor yang sedang dipanggil dan daftar menunggu. Auto-refresh dan privacy-safe.
   
   LOCATION: Ruang tunggu per cabang (1 TV untuk semua spesialis per cabang)
   
   DISPLAY LAYOUT:
   Nama Dokter | Spesialis | Sesi
   NOW: [Nomor sedang dipanggil - merah highlight]
   QUEUE: [Daftar nomor menunggu - biru normal]
   [Spacer]
   [repeat untuk 8 dokter]
   
   EXAMPLE:
   ```
   ┌─────────────────────────────────────────────────────────┐
   │  TV QUEUE DISPLAY - ANTRIAN HARI INI                    │
   ├─────────────────────────────────────────────────────────┤
   │                                                           │
   │  Dr. Siti Nurhaliza | Sp.BM (Bedah Mulut)| 09:00-12:00 │
   │  NOW: 05  QUEUE: 06  07  08  09                          │
   │                                                           │
   │  Dr. Budi Santoso | Sp.KG (Konservasi) | 09:00-12:00    │
   │  NOW: 03  QUEUE: 04  05                                  │
   │                                                           │
   │  Dr. Rina Wijaya | Sp.KGA (Anak) | 13:00-16:00          │
   │  NOW: 02  QUEUE: 03  04  05  06                          │
   │                                                           │
   │  Dr. Ahmad Hidayat | Sp.PM (Penyakit Mulut) | 13:00-16:00│
   │  NOW: --  QUEUE: 01  02  03                              │
   │                                                           │
   │  [Spesialis 5-8 ...similar format...]                    │
   │                                                           │
   └─────────────────────────────────────────────────────────┘
   ```
   
   REAL-TIME UPDATES:
   - Trigger: Setiap state change (check-in, panggil, selesai)
   - Method: WebSocket push ke TV display client
   - Fallback: Polling setiap 2-3 detik (HTTP GET)
   - Refresh rate: < 1 detik (WebSocket), <= 3 detik (polling)
   
   STATE MACHINE:
   ```
   [Check-in] → WAITING → [Dokter panggil] → BEING_CALLED → [Selesai] → COMPLETED [delete dari display]
   ```
   
   AUTO-DELETE BEHAVIOR:
   - Saat dokter klik "Selesai" untuk nomor 05
   - Status update: BEING_CALLED → COMPLETED
   - TV display otomatis delete nomor 05 (tidak show sama sekali)
   - Nomor 06 promote ke "NOW" position
   - Rest: 07, 08, 09 tetap di QUEUE
   
   COLOR CODING:
   - NOW (merah/highlight): Nomor yang sedang dilayani
   - QUEUE (biru/normal): Nomor yang menunggu
   
   PRIVACY:
   - ONLY display nomor urut (queue_number)
   - JANGAN display nama pasien
   - JANGAN display detail pasien apapun
   - Compliance: Privasi data pasien terjaga
   
   MULTI-SPESIALIS LAYOUT:
   - Cabang dengan 8 spesialis: 2-column grid atau 3-column (responsive)
   - Each spesialis: dedicated box dengan layout NOW/QUEUE
   - If session not active: grey out atau hidden
   
   SESSION TIMING:
   - Display: Nama dokter, Spesialis, Sesi (09:00-12:00)
   - End-of-session: Otomatis hide setelah sesi berakhir
   - Next session: Otomatis show ketika session dimulai
   
   API ENDPOINT (TV DISPLAY):
   GET /api/branches/{branch_id}/queue-display
   - Return: {
       sessions: [
         {
           doctor_id, doctor_name, specialist, session_time_start, session_time_end,
           now_queue_number (atau null),
           waiting_queue_numbers: [06, 07, 08, 09]
         }
       ]
     }
   - No auth required (public display)
   - Cache: 3 detik (atau real-time WebSocket)
   
   WEBSOCKET (RECOMMENDED):
   - Namespace: /queue-display
   - Events:
     - queue-updated: {doctor_id, now_number, queue_numbers}
     - queue-completed: {doctor_id, completed_number}
   - Broadcast: To all TV display clients per cabang
   
   EDGE CASES:
   - No queue nomor (sesi baru): Show "Menunggu pasien pertama..."
   - Doctor tidak ada (hari libur): Hide session
   - Multiple sesi 1 dokter: Show upcoming session preview (opsional V2)
   
   HARDWARE SETUP (Optional):
   - TV size: 43" atau 55" (landscape orientation)
   - Resolution: 1920x1080 (HD) minimal
   - Device: Raspberry Pi atau Android TV Box
   - Connection: Ethernet (recommended) atau WiFi
   - Browser: Chromium/Chrome kiosk mode

   TRIGGER:
   Saat dokter mengklik "COMPLETED" pada EMR form
   
   PROCESS:
   1. Dokter finish enter EMR details (Keluhan, Tindakan, Resep)
   2. Dokter click "Simpan & Selesai"

   4. EMR status: DRAFT → COMPLETED

   7. Audit log: EVENT_INVOICE_GENERATED
   8. Admin notification: New invoice available

5.6 EMR WORKFLOW (REVISED - v10)

   EMR dibuat SETELAH dokter selesai treatment, bukan sebelum.

   5. EMR form open (pre-filled: pasien name, tanggal, dokter, session time)
   6. Dokter input: Keluhan, Tindakan (dropdown + notes), Resep/Anjuran

   8. Dokter click "Simpan & Selesai"
   9. EMR status: DRAFT → COMPLETED
   10. AUTO-TRIGGER: Invoice generation
   11. Queue status: BEING_CALLED → COMPLETED
   12. TV display: Auto-delete nomor
   13. Pasien notification: "Sesi selesai, invoice siap bayar"

   - HIDDEN: Diagnosa (internal only)

6. USER STORIES & ACCEPTANCE CRITERIA

6.1 PAYMENT GATEWAY

USER STORY: Pasien membayar DP via Payment Gateway
AS A Pasien
I WANT TO pay DP Rp 50.000 via Midtrans payment gateway
SO THAT sistem otomatis confirm booking tanpa admin waiting time

ACCEPTANCE CRITERIA:
- Given pasien completed booking, When pasien click "Bayar Sekarang", Then pasien redirect ke Midtrans payment page
- Given pasien di Midtrans page, When pasien select payment method dan submit, Then payment simulated (sandbox)
- Given payment submitted, When Midtrans send webhook confirmation, Then booking status update to PAYMENT_CONFIRMED
- Given payment confirmed, When system process webhook, Then pasien see booking confirmation page (kode + dokter + spesialis + jadwal)
- Given pasien confirm, When pasien click "Mengerti", Then pasien redirect to booking history (payment completed)
- Given webhook failed, When system retry 3x, Then admin alert jika failed persistent
- Given pasien abandon payment, When 24 jam timeout, Then booking auto-cancel (PENDING_PAYMENT status)

6.2 MANDATORY CHECK-IN

USER STORY: Admin input kode booking untuk check-in pasien
AS AN Admin
I WANT TO input kode booking untuk check-in pasien
SO THAT antrian terjaga kondusif dan pasien tercatat dengan jelas

ACCEPTANCE CRITERIA:
- Given pasien datang ke klinik, When pasien beri kode booking ke admin, Then admin input kode di admin panel
- Given admin input kode, When system validate kode, Then nomor antrian auto-generated (jika valid)
- Given nomor generated, When system process, Then nomor appear di admin screen & TV display & pasien mobile (real-time)
- Given kode sudah check-in sebelumnya, When admin input lagi, Then system show "Sudah check-in, nomor: 05"
- Given kode invalid/expired, When system validate, Then show error dengan detail reason
- Given walk-in pasien, When admin click "Add Walk-in", Then admin input nama & spesialis (auto-generate kode & queue)
- Given queue number generated, When FCM push, Then pasien receive notification "Nomor antrian: 05"

6.3 TV QUEUE DISPLAY

USER STORY: Pasien lihat antrian real-time di TV ruang tunggu
AS A Pasien
I WANT TO see antrian real-time per spesialis di TV ruang tunggu
SO THAT saya tahu posisi antrian saya dan estimasi waktu tunggu

ACCEPTANCE CRITERIA:
- Given TV display active, When sesi dokter mulai, Then display show semua dokter dengan format: Nama | Spesialis | Sesi
- Given pasien check-in, When nomor antrian generated, Then nomor appear di TV display (QUEUE section)
- Given dokter panggil nomor 05, When dokter click "Panggil", Then TV display update: NOW: 05, QUEUE: 06 07 08
- Given dokter selesai treatment nomor 05, When dokter click "Selesai", Then nomor 05 auto-delete dari display
- Given nomor deleted, When display refresh, Then nomor 06 promote ke NOW, rest stay QUEUE
- Given WebSocket down, When TV polling active, Then display update setiap 2-3 detik (fallback)
- Given sesi selesai, When waktu > 12:00, Then sesi auto-hide atau grey out
- Given pasien view display, When pasien see nomor, Then ONLY nomor displayed (no names, privacy safe)

6.4 AUTO-INVOICE

USER STORY: Invoice otomatis generate saat EMR completed
AS AN Admin/Dokter
I WANT TO invoice auto-generated saat EMR selesai
SO THAT admin tidak perlu manual create invoice, dan payment tracking jelas

ACCEPTANCE CRITERIA:
- Given dokter selesai isi EMR, When dokter click "Simpan & Selesai", Then invoice auto-generated
- Given invoice generated, When system process, Then invoice appear di admin panel (list unpaid)
- Given invoice created, When invoice status check, Then status = UNPAID (default)
- Given admin view invoice, When admin open detail, Then show breakdown: DP + Treatment cost + Total
- Given pasien bayar, When admin input payment (nominal + metode), Then invoice status → PAID
- Given invoice paid, When timestamp record, Then paid_at recorded (audit trail)
- Given dokter view invoice, When dokter open portal, Then invoice show (read-only, informational)

6.5 ROLE-BASED MENU

USER STORY: Dokter tidak punya akses menu Stok/Inventaris
AS A Dokter
I WANT TO fokus pada patient care tanpa inventory responsibility
SO THAT workflow lean dan tidak overburden dengan administrative tasks

ACCEPTANCE CRITERIA:
- Given dokter login, When dokter view menu, Then Stok/Inventaris menu NOT visible
- Given admin login, When admin view menu, Then Stok/Inventaris menu visible

12. RISK MANAGEMENT & MITIGATION

🟢 CRITICAL (Impact: HIGH, Probability: MEDIUM)

Risk: Midtrans webhook tidak arrive (network failure)
Mitigasi:
- Implement webhook signature verification (Midtrans standard)
- Retry logic: 3x exponential backoff
- Client-side polling fallback (check status every 5 detik)
- Webhook timeout handler: booking stay PENDING_PAYMENT, pasien can retry
- Admin alert jika webhook fail persistent (>5x)

Risk: Check-in kode digunakan 2x (duplicate)
Mitigasi:
- Database constraint: UNIQUE check_in_code
- Validation before processing: IF queue_number EXIST → error "sudah check-in"
- Audit log track semua check-in attempt
- Prevent re-use: check_in_status field (PENDING | USED | EXPIRED)

Risk: TV display offline (power loss, WiFi down)
Mitigasi:
- Fallback: Paper queue board (manual backup)
- Hardware: UPS untuk TV + router
- Reconnect logic: Auto-reconnect setiap 30 detik
- Last-known state: Display show cached data jika offline

Risk: Database size exceed 2GB (Supabase free limit)
Mitigasi:
- Monitor database size weekly
- Cleanup: Delete old audit logs (>1 year) monthly
- Setup alert: 80% quota trigger
- Fallback: Upgrade ke paid tier (post-demo)

Risk: Booking state mismatch (PENDING_PAYMENT vs PAYMENT_CONFIRMED)
Mitigasi:
- Webhook idempotency: Check IF booking.status != PAYMENT_CONFIRMED before update
- Database transaction: Atomic update (no race condition)
- Audit log: Track every status change dengan timestamp

🟡 MEDIUM (Impact: MEDIUM, Probability: MEDIUM)

Risk: Admin input wrong kode (typo)
Mitigasi:
- Validation error message: Clear feedback dengan reason
- Case-insensitive kode matching (user-friendly)
- Confirm dialog sebelum submit
- Audit log: Track failed attempts (security & troubleshooting)

Risk: Pasien abandon payment halfway (Midtrans timeout)
Mitigasi:
- Booking stay PENDING_PAYMENT (tidak auto-cancel immediately)
- Display: "Pembayaran pending, Anda bisa retry kapan saja dalam 24 jam"
- Cron job: Auto-cancel booking jika PENDING_PAYMENT > 24 jam
- Pasien notification: Reminder email/FCM sebelum timeout

Risk: Walk-in queue overload (lebih dari 4 per sesi)
Mitigasi:
- Admin bisa add multiple walk-in (sistem memungkinkan)
- No hard limit (pragmatic: biar dokter manage sendiri)
- Audit log: Track jumlah walk-in per sesi (data untuk optimization)
- Recommend V2: Walk-in limiter atau priority logic

🟢 LOW (Impact: LOW, Probability: LOW)

Risk: Ngrok tunnel expire / reconnect
Mitigasi:
- Ngrok paid tier untuk production (tapi V1 sandbox OK dengan free)
- Fallback: Switch ke alternative tunnel service jika needed
- Update webhook URL manually jika ngrok restart

Risk: Invoice number collision (duplicate INV-CABANGA-20260707-001)
Mitigasi:
- Database sequence: Auto-increment per branch per day
- Unique constraint: (branch_id, invoice_date, sequence)
- Format: INV-[CABANG]-[YYYYMMDD]-[SEQUENCE PADDED 3 DIGIT]

16. GLOSARIUM

6-DIGIT KODE: Alfanumerik unik (A-Z, 0-9) pengganti QR untuk check-in pasien, dibuat saat booking, diivalidasi oleh admin

SPESIALIS: 8 dokter gigi spesialis per cabang
- Sp.BM (Bedah Mulut)
- Sp.KGA (Kedokteran Gigi Anak)
- Sp.KG (Konservasi Gigi)
- Sp.PM (Penyakit Mulut)
- Sp.Ort (Ortodonti)
- Sp.Perio (Periodonsia)
- Sp.Pros (Prostodonsia)
- Sp.RKG (Radiologi)

SESI: Time slot praktek dokter (misal 09:00-12:00, 13:00-16:00)

EMR: Electronic Medical Record (rekam medis digital)

ENCOUNTER: Satu kali kunjungan pasien ke dokter (satu sesi EMR)

DP (DOWN PAYMENT): Rp 50.000 (non-refundable, konfirmasi booking via payment gateway)

PAYMENT GATEWAY: Sistem pembayaran online (Midtrans) untuk DP confirmation otomatis

WEBHOOK: HTTP callback dari Midtrans ke backend untuk payment status update

NO SHOW: Pasien tidak check-in hingga akhir sesi, DP hangus

WALK-IN: Pasien datang tanpa booking sebelumnya

FIFO: First In First Out (antrian berdasarkan urutan check-in)

QUEUE: Antrian pasien per dokter spesialis

TV QUEUE DISPLAY: Real-time antrian display di TV ruang tunggu (nomor urut only, no names)

FCM: Firebase Cloud Messaging (push notification)

AUDIT LOG: Catatan immutable (append-only) semua aktivitas sistem

BRANCH_ID: Identifier cabang (A, B, atau C) untuk multi-tenant isolation

IDEMPOTENT: Request yang sama tidak akan diproses 2x (prevent duplicate)

JWT: JSON Web Token (authentication token)

BCRYPT: Password hashing algorithm (security standard)

MODULITH: Modular monolith (monolith dengan domain separation)

INVOICE: Dokumen billing otomatis saat EMR completed (DP + Treatment cost)

INVENTORY/STOK: Item management (admin only, tidak untuk dokter)
