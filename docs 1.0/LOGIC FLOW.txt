DETAILED LOGIC:

STEP 1: BOOKING CREATION
┌─────────────────────────────────────────────────────────────┐
│ Pasien Input:                                               │
│ - Cabang, Spesialis, Tanggal, Sesi                          │
│ - System validate: Jadwal exist? Slot available? (Max 4)    │
│ - IF valid: Create booking record                           │
│   Status: PENDING_PAYMENT                                   │
│   DP Amount: Rp 50.000                                      │
│   Check-in Code: Generate 6-digit (36^6 = 2.1B kombinasi)  │
│ - Audit log: BOOKING_CREATED event                          │
└─────────────────────────────────────────────────────────────┘

STEP 2: PAYMENT REDIRECT
┌─────────────────────────────────────────────────────────────┐
│ Pasien Click "Bayar Sekarang"                               │
│ Request: POST /api/bookings/{id}/payment-redirect           │
│ Backend Logic:                                              │
│   1. GET booking by ID                                      │
│   2. Validate: status == PENDING_PAYMENT?                   │
│   3. Create Midtrans transaction request:                   │
│      - transaction_id (unique)                              │
│      - amount: 50000 (Rp)                                   │
│      - customer_email: pasien.email                         │
│      - item: "DP Booking Klinik Gigi"                       │
│   4. Call Midtrans API: POST /v2/transactions               │
│   5. Response: redirect_url from Midtrans                   │
│   6. Save payment_gateway_id ke booking record              │
│   7. Return redirect_url to frontend                        │
│ Frontend: window.location = redirect_url (Midtrans page)   │
│ - Audit log: PAYMENT_REDIRECT event                        │
└─────────────────────────────────────────────────────────────┘

STEP 3: PAYMENT PROCESSING (SANDBOX)
┌─────────────────────────────────────────────────────────────┐
│ Pasien di Midtrans Payment Page:                            │
│ 1. Select payment method (simulated, sandbox)               │
│ 2. Enter details (fake data OK for sandbox)                 │
│ 3. Click "Bayar/Process"                                    │
│ Midtrans:                                                   │
│ 4. Process payment (instant dalam sandbox)                  │
│ 5. Generate transaction status: SETTLEMENT                  │
│ 6. Send webhook to backend                                  │
│    POST https://[ngrok-tunnel]/webhook/payment-confirmation │
│    Body: {                                                  │
│      transaction_id: "xxx",                                 │
│      order_id: "booking_id",                                │
│      status_code: "200",                                    │
│      transaction_status: "settlement",                      │
│      signature_key: "hash"                                  │
│    }                                                        │
│ - Audit log: PAYMENT_PROCESSED event (at Midtrans)         │
└─────────────────────────────────────────────────────────────┘

STEP 4: WEBHOOK HANDLER (CRITICAL)
┌─────────────────────────────────────────────────────────────┐
│ Backend Webhook Endpoint:                                   │
│ POST /webhook/payment-confirmation                          │
│                                                             │
│ VALIDATION PHASE:                                          │
│ 1. Extract: order_id, transaction_status, signature_key    │
│ 2. Generate expected_signature (using Midtrans server_key) │
│ 3. IF signature_key != expected_signature:                  │
│    REJECT webhook, log error, return 403 Forbidden         │
│ 4. ELSE: Signature valid, proceed                          │
│                                                             │
│ UPDATE PHASE:                                              │
│ 5. Fetch booking by order_id                               │
│ 6. Check: booking.status == PENDING_PAYMENT?               │
│    IF NOT: Duplicate webhook, skip update, return 200 OK   │
│    (Idempotency: prevent duplicate status update)          │
│ 7. IF status == SETTLEMENT or CAPTURE:                     │
│    - Update booking.status → PAYMENT_CONFIRMED             │
│    - Update booking.payment_status → PAYMENT_CONFIRMED     │
│    - Set booking.payment_confirmed_at = NOW()              │
│    - Save to database (atomic transaction)                 │
│ 8. IF status == PENDING:                                   │
│    - Keep booking.status PENDING_PAYMENT                   │
│    - Continue polling (pasien will retry)                  │
│ 9. IF status == DENY or EXPIRE:                           │
│    - Update booking.status → PAYMENT_FAILED                │
│    - Notify pasien: Payment gagal, coba lagi               │
│                                                             │
│ NOTIFICATION PHASE:                                        │
│ 10. Send FCM push to pasien:                               │
│     Title: "Pembayaran Berhasil"                           │
│     Body: "Kode Booking: ABC123"                           │
│ 11. Audit log: PAYMENT_CONFIRMED event                     │
│ 12. Return 200 OK to Midtrans (webhook success)            │
│                                                             │
│ ERROR HANDLING:                                            │
│ IF exception during update:                                │
│ - Log error                                                │
│ - Return 500 to Midtrans (trigger retry)                   │
│ - Retry max 3x dengan exponential backoff                  │
│ - IF persistent: Alert admin                               │
└─────────────────────────────────────────────────────────────┘

STEP 5: CLIENT-SIDE POLLING (FALLBACK)
┌─────────────────────────────────────────────────────────────┐
│ Mobile/Web Frontend:                                        │
│ 1. Pasien at Midtrans page                                 │

ERROR SCENARIOS:

Scenario A: WEBHOOK TIDAK SAMPAI
├─ Webhook sent 3x oleh Midtrans (automatic retry)
├─ Backend masih menerima, process normal
└─ Result: Payment confirmed (even jika late)

Scenario B: DUPLICATE WEBHOOK
├─ Midtrans send webhook 2x (network retry)
├─ Backend check: booking.status == PAYMENT_CONFIRMED?
├─ IF YES: Skip update (idempotent), return 200 OK
└─ Result: No duplicate status update

Scenario C: SIGNATURE MISMATCH (SECURITY)
├─ Webhook signature invalid (hijacked request?)
├─ Backend: Log error, reject webhook, return 403
├─ Alert: Admin notified tentang suspicious request
└─ Result: Booking status NOT updated (safe)

Scenario D: NETWORK ERROR DURING WEBHOOK
├─ Backend exception saat update database
├─ Return 500 to Midtrans (trigger automatic retry)
├─ Retry up to 3x dengan exponential backoff
├─ IF persistent: Admin alert + manual investigation
└─ Result: Eventually consistent (event-driven recovery)

Scenario E: PASIEN ABANDON PAYMENT
├─ Pasien navigate away dari Midtrans page
├─ Booking stay PENDING_PAYMENT (24 jam timeout)
├─ Pasien can retry anytime dalam 24 jam
├─ Cron job: Auto-cancel setelah 24 jam
└─ Result: Slot released, dapat dibook ulang pasien lain

2. BOOKING & CHECK-IN FLOW
================================================================

PART A: BOOKING SYSTEM

Pasien selects cabang → spesialis → tanggal → sesi
System validate availability (max 4 per sesi)
Generate 6-digit kode booking
Create booking record: status = PENDING_PAYMENT

(After payment confirmed, booking.status = PAYMENT_CONFIRMED)

Timeline:
Day 0: Pasien booking + payment

       09:00: Pasien datang ke klinik

│ 1. Query: SELECT booking WHERE check_in_code = "ABC123DEF" │
│    IF not found: Return error "Kode tidak valid"           │

│    IF != PAYMENT_CONFIRMED:                                │

│    IF queue_status IN (WAITING, BEING_CALLED):            │
│    Return info "Anda sudah check-in, nomor: 05"            │
│    STOP (prevent duplicate check-in)                       │
│                                                             │
│ 5. ALL VALIDATIONS PASSED:                                 │
│    - Generate queue_number using Redis INCR atomic counter │
│      Key: "queue:{branch_id}:{dokter_id}:{session_date}"   │
│      Result: queue_number = 05                             │
│                                                             │
│    - Create queue record:                                  │

│                                                             │
│    - Update booking:                                       │
│      booking.status = CHECKED_IN                           │
│      booking.queue_number = 05                             │
│      booking.checked_in_at = NOW()                         │
│                                                             │
│    - Audit log: CHECK_IN_SUCCESS event                     │
│      Details: {booking_id, pasien_name, dokter_name,       │
│                queue_number, check_in_time}               │
│                                                             │
│    - Return success response:                              │
│      {queue_number: 05, pasien_name: "Budi Santoso",      │
│       dokter_name: "drg. Siti Nurhaliza",                  │
│       specialist: "Sp.BM"}                                │

VALIDATION ERROR SCENARIOS:

Error 1: KODE TIDAK VALID
├─ Scenario: Pasien input salah kode (typo)
├─ Response: "Kode booking tidak ditemukan"
├─ Action: Admin ask pasien ulang input kode
└─ Audit: CHECK_IN_FAILED - INVALID_CODE

Error 2: KODE SUDAH DIPAKAI
├─ Scenario: Pasien input kode yang sudah check-in
├─ Response: "Anda sudah check-in, nomor: 05"
├─ Action: Show nomor antrian yang sudah ada
└─ Audit: CHECK_IN_DUPLICATE - ALREADY_CHECKED_IN

Error 3: PEMBAYARAN BELUM DIKONFIRMASI
├─ Scenario: Booking status masih PENDING_PAYMENT
├─ Response: "Pembayaran belum dikonfirmasi"
├─ Action: Admin ask pasien konfirmasi pembayaran dulu
└─ Audit: CHECK_IN_FAILED - PAYMENT_NOT_CONFIRMED

Error 4: SESI SUDAH BERAKHIR
├─ Scenario: Pasien datang setelah jam 12:00 (sesi 09:00-12:00)
├─ Response: "Sesi sudah berakhir"
├─ Action: Offer next available session / walk-in booking
└─ Audit: CHECK_IN_FAILED - SESSION_EXPIRED

Error 5: SESI BELUM DIMULAI
├─ Scenario: Pasien datang sebelum jam 09:00
├─ Response: "Sesi belum dimulai, silakan datang nanti"
├─ Action: Ask pasien tunggu / datang nanti
└─ Audit: CHECK_IN_FAILED - SESSION_NOT_STARTED

┌─────────────────────────────────────────────────────────────┐

│      checked_in_at: NOW(),                                  │

│                                                             │
│ 6. Create queue record:                                     │
│    queue {                                                  │
│      booking_id: (walk-in booking),                         │
│      dokter_id: 50,                                         │
│      queue_number: 04,                                      │
│      queue_status: WAITING,                                 │
│      check_in_time: NOW(),                                  │
│    }                                                        │
│                                                             │
│ 7. Audit log: WALK_IN_ADDED event                          │
│    Details: {pasien_name, specialist, queue_number, input_by}│

END OF LOGIC FLOW DOCUMENTATION
================================================================

SUMMARY:

1. PAYMENT GATEWAY FLOW:
   Midtrans webhook → backend validate → booking confirmed → pasien see kode

2. CHECK-IN FLOW:
   Pasien datang → admin input kode → validate → generate queue number

3. QUEUE MANAGEMENT:
   Check-in (WAITING) → Panggil (BEING_CALLED) → Selesai (COMPLETED, auto-delete)

4. EMR & INVOICE:
   EMR COMPLETED → Auto-generate invoice → Admin input payment

5. TV DISPLAY:
   Real-time queue per dokter, auto-delete nomor selesai, privacy-safe (no names)

6. WALK-IN:
   Admin add walk-in → Generate kode & queue → Same as booking process

7. RECONCILIATION:
   Daily/monthly: Compare physical cash + transfer dengan invoice records

All flows are designed untuk:
✓ Automation (no manual bottlenecks)
✓ Real-time updates (WebSocket + fallback polling)
✓ Data integrity (atomic transactions, audit logs)
✓ Privacy & security (no patient names in public displays)
✓ Operational efficiency (clear role separation)
✓ Compliance & auditability (immutable records)
