   ID : TD-TEST-006 (SUDAH DIPERBAIKI)
   Judul : Integration Test Check-in (Test 4) Di-Skip karena Butuh Mock Date
   Deskripsi : Test `tests/integration/booking-flow.e2e.test.ts` Test 4 
               (Admin check-in) di-skip menggunakan `.skip()` karena 
               membutuhkan mock date untuk validasi session time.
               
               **Detail Teknis:**
               - bookingDate di test = '2026-08-10' (masa depan)
               - Backend menggunakan `new Date()` untuk validasi `NOW()` 
                 terhadap `session_start` dan `session_end`.
               - Tanpa mock date, test throw error "SESI_BELUM_DIMULAI" 
                 karena `now (2026-07-28) < session_start (2026-08-10)`.
               
               **Upaya Perbaikan yang Gagal:**
               - Sudah dicoba menggunakan `jest.useFakeTimers()` dan 
                 `jest.setSystemTime()` di `beforeAll`.
               - Namun menyebabkan connection pool `pg` dan Redis client 
                 (`ioredis`) hang karena fake timers mengganggu internal 
                 heartbeat, retry timers, dan keepalive mechanism.
               - Akibatnya Test 8 (Complete Encounter) timeout 60 detik.
               - Solusi fake timers global ini **tidak viable** untuk 
                 integration test dengan database real.
   Dampak : 
               - Endpoint `/api/admin/check-in` (P0 feature) tidak ter-cover 
                 oleh integration test automation di CI.
               - Risiko regression di production karena perubahan kode 
                 check-in tidak terdeteksi oleh test suite.
               - Total test suite berjalan 10/12 (83.3%), tidak mencapai 
                 target 100% untuk P0 features.
   Perbaikan : 
               **Pendekatan Mature di Phase 3:**
               1. Buat utility `src/utils/time.ts`:
                  ```typescript
                  export const getCurrentTime = () => {
                    if (process.env.NODE_ENV === 'test' && process.env.MOCK_DATE) {
                      return new Date(process.env.MOCK_DATE);
                    }
                    return new Date();
                  };
                  ```
               2. Replace semua `new Date()` di service layer dengan 
                  `getCurrentTime()` (terutama yang berkaitan dengan 
                  validasi sesi, invoice generation, audit log timestamp).
               3. Di test, cukup set `process.env.MOCK_DATE = '2026-08-10T09:30:00'` 
                  **tanpa** `jest.useFakeTimers()` agar tidak mengganggu 
                  koneksi database.
               4. Hapus `.skip` dari Test 4 dan aktifkan kembali.
               5. Verifikasi 12/12 passed tanpa hang.
               
               **Alternatif (Jika Refactor Terlalu Besar):**
               - Gunakan `sinon.useFakeTimers()` yang lebih controllable 
                 (dengan `{ shouldAdvanceTime: true }`).
               - Atau pindahkan check-in test ke unit test dengan mock 
                 repository, bukan integration test.
   Estimasi : 2-3 jam (refactor time utility + update test)
   Prioritas : HIGH

   2.6. PAYMENT WEBHOOK (TASK 2.4.1)
   ──────────────────────────────────────────────────────────────
   ID : TD-PAY-001 (SUDAH DIPERBAIKI)
   Judul : Webhook Integration Test Di-Skip (describe.skip)
   Deskripsi : Test `tests/integration/webhook.integration.test.ts` di-skip 
               (describe.skip) karena butuh setup data kompleks 
               (branch, patient, doctor, booking, encounter, invoice) 
               yang tidak stabil di CI.
   Dampak : Tidak ada automation test end-to-end untuk webhook Midtrans 
            di pipeline CI. Hanya unit test yang mencakup logic signature 
            dan idempotency.
   Perbaikan : Refactor test setup dengan factory/seed yang idempoten, 
               atau gunakan testcontainers untuk database terisolasi.
   Estimasi : 3-4 jam
   Prioritas : HIGH

   ID : TD-PAY-002 (SUDAH DIPERBAIKI)
   Judul : Signature Validation Hanya Menggunakan Payload String (Bukan Standar Midtrans)
   Deskripsi : Midtrans signature seharusnya dihitung dari kombinasi 
               `order_id`, `status_code`, `gross_amount`, dan `server_key`.
               Saat ini kita hanya menggunakan raw payload string, yang 
               tidak sesuai dengan standar Midtrans.
   Dampak : Signature validation bisa gagal di production jika Midtrans 
            mengubah format payload, atau rentan terhadap replay attack.
   Perbaikan : Update `validateMidtransSignature()` untuk menggunakan 
               formula standar Midtrans:
               `SHA256(order_id + status_code + gross_amount + server_key)`.
   Estimasi : 1-2 jam
   Prioritas : HIGH

   ID : TD-PAY-003 (SUDAH DIPERBAIKI)
   Judul : Idempotency Key Tidak Menggunakan `x-midtrans-webhook-id` dari Header
   Deskripsi : Midtrans mengirim header `x-midtrans-webhook-id` yang 
               seharusnya digunakan sebagai idempotency key. Saat ini 
               kita generate `webhookId` sendiri atau menggunakan 
               `transaction_id` dari payload.
   Dampak : Potensi duplicate processing jika Midtrans mengirim webhook 
            yang sama dengan `transaction_id` berbeda (misal retry).
   Perbaikan : Gunakan `x-midtrans-webhook-id` dari header sebagai 
               primary idempotency key, fallback ke `transaction_id`.
   Estimasi : 1 jam
   Prioritas : MEDIUM

   ID : TD-PAY-004 (SUDAH DIPERBAIKI)
   Judul : Retry Mechanism Belum Diuji dengan Integration Test
   Deskripsi : `PaymentWebhookService.retryFailedWebhooks()` ada, tapi 
               belum ada integration test yang memverifikasi cron job 
               berjalan dan retry berhasil.
   Dampak : Risiko webhook gagal tidak terdeteksi sampai production, 
            dan retry logic tidak terjamin.
   Perbaikan : Tambahkan integration test yang mensimulasikan webhook 
               error, kemudian trigger retry job dan verifikasi status 
               berubah menjadi PROCESSED.
   Estimasi : 2-3 jam
   Prioritas : MEDIUM

   ID : TD-PAY-005 (SUDAH DIPERBAIKI)
   Judul : Webhook Handler Tidak Membedakan Status Transaksi (capture, settlement, deny, expire)
   Deskripsi : Saat ini webhook hanya memproses jika status = 'capture' 
               atau 'settlement'. Status lain (deny, expire) tidak 
               ditangani dengan baik.
   Dampak : Booking yang gagal (deny/expire) tidak otomatis di-cancel, 
            dan pasien tidak mendapat notifikasi.
   Perbaikan : Tambahkan logika untuk handle semua status transaksi:
               - capture/settlement → mark paid
               - deny/expire → mark failed, cancel booking
               - pending → keep status, retry later
   Estimasi : 2 jam
   Prioritas : MEDIUM

   ID : TD-PAY-006 (SUDAH DIPERBAIKI)
   Judul : Invoice Lookup Hanya Berdasarkan `invoice_number` dan `booking_id`
   Deskripsi : `PaymentWebhookService` mencari invoice berdasarkan 
               `order_id` yang dianggap sebagai `invoice_number` atau 
               `booking_id`. Tidak ada fallback jika invoice tidak ditemukan.
   Dampak : Webhook akan gagal jika invoice_number tidak tersimpan di DB 
            (masih dari TDD-TD-DB-001) atau jika order_id format berubah.
   Perbaikan : Pastikan tabel `invoices` memiliki kolom `invoice_number` 
               (TD-DB-001), dan update webhook untuk mencari berdasarkan 
               `invoice_number` dengan parsing yang tepat.
   Estimasi : 2 jam (tergantung TD-DB-001)
   Prioritas : HIGH

   ID : TD-PAY-007 (SUDAH DIPERBAIKI)
   Judul : Tidak Ada Webhook untuk Payment Failure / Refund
   Deskripsi : Midtrans mengirim webhook untuk refund dan failure, 
               tapi kita hanya handle payment success.
   Dampak : Jika payment refund terjadi, invoice tetap status PAID 
            dan tidak ada audit trail untuk refund.
   Perbaikan : Tambahkan handler untuk webhook refund dan failure, 
               dengan state machine yang sesuai (PAID → REFUNDED).
   Estimasi : 2-3 jam
   Prioritas : LOW (bisa V2)

   ID : TD-PAY-008 (SUDAH DIPERBAIKI)
   Judul : Webhook Endpoint Tidak Menggunakan Rate Limiting Khusus
   Deskripsi : Endpoint `/webhooks/midtrans` menggunakan global rate 
               limiter (5 req/sec), yang mungkin terlalu rendah untuk 
               burst webhook dari Midtrans.
   Dampak : Webhook legitimate bisa ditolak (429) jika Midtrans mengirim 
               banyak webhook dalam waktu singkat.
   Perbaikan : Buat rate limiter khusus untuk webhook endpoint dengan 
               limit lebih tinggi (misal 50 req/sec) atau disable 
               rate limiting untuk endpoint ini.
   Estimasi : 30 menit
   Prioritas : LOW

   ID : TD-ARCH-003
   Judul : Patient Web Portal Terlanjur Dibangun (Padahal Hanya untuk Flutter)
   Deskripsi : 
               Berdasarkan PRD v10.0, pasien HANYA memiliki akses melalui 
               aplikasi mobile (Flutter). Namun dalam implementasi Phase 3,

               - Dashboard pasien (Task 3.1.11)
               - Riwayat EMR (Task 3.2.1)
               - Invoices & Payment History (Task 3.2.2)
               - Appointment Management (Task 3.2.3)
               - Profile & Settings (Task 3.2.4)
               - AI Chat Assistant (Task 3.2.5)
               
               Ini adalah **DEVIASI DARI PRD** yang menyebabkan:
               - Duplikasi effort (Flutter akan dibangun ulang dengan fitur yang sama)
               - Potensi inkonsistensi fitur antara web dan mobile
               - Kode "sampah" di Next.js yang seharusnya tidak ada
               - Beban maintenance tambahan
               
   Dampak : 
               - **Code Bloat:** ~500-1000 lines of unnecessary code di Next.js
               - **Testing Overhead:** Harus menulis E2E test untuk patient web padahal seharusnya tidak
               - **Confusion:** Developer/recruiter yang lihat kode akan bingung "kok ada patient web?"
               - **Risk of Divergence:** Jika ada perubahan fitur, harus di-update di 2 tempat (web + mobile)
               - **Delivery Delay:** Waktu yang terbuang untuk build patient web seharusnya dipakai untuk Flutter
               
   Keputusan : 
               **Kode patient web TIDAK DIHAPUS** (karena sudah terlanjur), tapi:
               1. **Di production:** Redirect semua akses `/patient/*` ke landing page (`/`) 
                  menggunakan Next.js middleware.
               2. **Di development/test:** Tetap diizinkan akses untuk keperluan E2E testing.
               3. **Tidak ada navigasi** ke `/patient/*` di manapun (navbar, sidebar, footer, CTA).
               4. **E2E test** tetap mencakup patient flow menggunakan route ini (di environment test).
               5. **Flutter tetap menjadi satu-satunya** akses pasien di production.
               6. **Setelah Flutter selesai dan stabil:** Hapus semua route `/patient/*` di Next.js.
               
   Perbaikan : 
               1. **Buat middleware** di Next.js (`src/middleware.ts`):
                  ```typescript
                  import { NextResponse } from 'next/server';
                  import type { NextRequest } from 'next/server';

                  export function middleware(request: NextRequest) {
                    const { pathname } = request.nextUrl;
                    
                    // Block patient routes in production
                    if (pathname.startsWith('/patient')) {
                      const isProduction = process.env.NODE_ENV === 'production';
                      if (isProduction) {
                        return NextResponse.redirect(new URL('/', request.url));
                      }
                      // In development/test, allow access
                      const response = NextResponse.next();
                      response.headers.set('X-Patient-Web-Access', 'allowed-for-testing');
                      return response;
                    }
                    
                    return NextResponse.next();
                  }

                  export const config = {
                    matcher: '/patient/:path*',
                  };
